# Rule: Coding Principles

## Summary

项目级编码基本原则，约束所有编码决策和实现方式。

## Rules

### 基础原则

- **KISS**：优先选择简单、直接、可读的实现。不要为了显得通用而引入复杂抽象、额外状态或难以追踪的控制流。
- **YAGNI**：不要为未确认的未来需求提前设计扩展点、配置项、fallback 或框架层。只有当前需求和稳定边界需要时才添加能力。
- **系统性修复**：遇到 bug 或异常行为时，先理解根因、数据流、调用边界和失败条件，再修改拥有该职责的模块。
- **避免 hack 和 ad-hoc fix**：不要通过硬编码特殊分支、绕过验证、吞掉异常、隐藏错误、伪造状态或只修表象的方式解决问题。

### 面向对象设计原则（SOLID）

- **单一职责原则（SRP）**：一个类应该只有一个引起变化的原因。每个类或模块只负责一项明确的职责，避免将不相关的逻辑耦合在一起。
- **开闭原则（OCP）**：软件实体应对扩展开放，对修改关闭。通过抽象和多态实现扩展，而非修改已有代码。
- **里氏替换原则（LSP）**：子类型必须能够替换其基类型而不破坏程序正确性。继承关系必须保证行为契约的一致性。
- **接口隔离原则（ISP）**：客户端不应被迫依赖它不使用的接口。将大接口拆分为更小、更具体的接口，让类只实现需要的方法。
- **依赖倒置原则（DIP）**：高层模块不应依赖低层模块，两者都应依赖抽象。抽象不应依赖细节，细节应依赖抽象。

### 模块划分原则

- **高内聚**：模块内部的元素应紧密相关，共同完成一个明确的职责。功能相关的代码应放在一起，避免分散。
- **低耦合**：模块间的依赖应尽可能少且清晰。通过明确的接口进行交互，避免隐式依赖和循环依赖。
- **职责边界清晰**：每个模块应有明确的职责边界，对外暴露最小化的公开接口，隐藏内部实现细节。
- **避免上帝模块**：不要创建承担过多职责的巨型类或模块。当一个类或模块的职责过多时，应进行拆分。

## Applies To

- 所有编码任务和代码变更。
- 所有模块和文件类型。

## Verification

- Code review 时检查是否违反以上原则。
- 发现 hack 或过度设计时，要求按原则修正。

## Reference Files

- 无特定文件；原则适用于整个项目。

## Non-Goals

- 不列举所有遵循这些原则的代码位置。
